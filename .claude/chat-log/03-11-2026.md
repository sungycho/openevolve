  ---                                                                                                
  ILS Engine — Design & Flow
                                                                                                     
  What it is                                                
                                                                                                     
  A standalone post-processing layer that takes a completed OpenEvolve run and tries to squeeze more 
  performance out of the best evolved programs via Iterated Local Search. It doesn't touch OpenEvolve
   internals — it just reads the output and runs independently.                                      
                                                            
  ---
  5-Step Pipeline
                 
  Step 0 — Program Selection (program_selector.py)
                                                                                                     
  Load programs from OpenEvolve output and pick the top-K most promising ones. Three modes:          
  - top_1: just grab the single best program                                                         
  - vanilla_top_k: take the top K by score                                                           
  - novelty_rejection: iterate by score, reject candidates that are too similar (by edit distance) to
   already-selected ones — avoids running ILS on near-duplicate programs                             
                                                                                                     
  Step 1 — ILS Analysis (ils_analyzer.py)                                                            
                                                                                                     
  Send the program code to the LLM and ask: does this program have a stochastic component that ILS   
  can exploit? Returns a structured spec describing the component — its name, type                   
  (continuous/discrete/constrained), location in the code, and degrees of freedom. If the program is 
  deterministic, it gets skipped.                           

  Step 2 — Strategy Planning (strategy_planner.py)                                                   
   
  Given the component spec, ask the LLM to design search strategies. Always produces two universal   
  ones:                                                     
  - perturb_best: add Gaussian noise to the best known solution, re-optimize from there              
  - random_restart: completely randomize the component, re-optimize from scratch                     
                                                                                
  Optionally (Tier 2) the LLM proposes domain-specific structured initializations — e.g. hexagonal   
  grid for circle packing — if it can justify them concretely. The seed budget is split across       
  strategies.                                                                                        
                                                                                                     
  Step 3 — Code Generation (code_generator.py)              

  For each strategy, ask the LLM to write a complete, standalone Python search script. The script:   
  implements the strategy, loops over seeds, calls the evaluator, and prints JSON-line results to
  stdout. Validated with ast.parse(), retried once on syntax error.                                  
                                                            
  Step 4 — Execution (runner.py)                                                                     
   
  Run all strategy scripts in parallel (one subprocess per strategy via ProcessPoolExecutor). Each   
  script handles its own internal seed parallelism. Parse the JSON-line stdout to collect per-seed
  scores and the overall best.                                                                       
                                                            
  Step 5 — Reporting (reporter.py)                                                                   
   
  Print a clean results table to terminal and save to ils_output/<task_name>/:                       
  - best_program.py — the best program found                
  - best_program_info.json — score, strategy, seed, improvement                                      
  - results_summary.json — full table                          
  - strategies/ — per-strategy breakdown                                                             
                                                                                                     
  ---                                                                                                
  Key Design Choices                                                                                 
                                                                                                     
  - Independent of OpenEvolve: uses only openevolve/database.py for loading programs, nothing else
  - LLM via OpenRouter: Steps 1–3 call the LLM sequentially (each depends on the prior); Step 4 is   
  parallel                                                                                           
  - Generated scripts are self-contained: they embed the original program code as a string and       
  generate modified versions at runtime — no file dependencies beyond the evaluator                  
  - Graceful degradation: syntax errors retry once; failed strategies are skipped but don't crash the
   run; fallback strategies exist if LLM JSON fails to parse
